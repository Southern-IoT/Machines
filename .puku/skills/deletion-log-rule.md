# Deletion-log rule — Southern Machines

> This rule applies to **every** file or directory removed from this
> repository, regardless of who removes it (human, AI agent, build script,
> editor, IDE) or how (rm, del, trash, fs.rmSync, os.remove, IDE delete,
> `git rm`, branch reset, etc.).

## The rule

**Any file or directory removed from the working tree MUST be appended
to `deleted_files.md` at the repo root before or immediately after the
removal**, with:

1. **Timestamp** — when it was removed (use `date -Iseconds` for ISO format).
2. **Path(s)** — every path removed (file or directory).
3. **Size** — `du -sh` output if the file/dir existed at removal time.
4. **Reason** — short one-line explanation (≤120 chars).

## How to comply

### Preferred: use the `del` shell function

The `del` function is defined at the bottom of `deleted_files.md`. Source
it once per session:

```bash
source <(tail -n +1 deleted_files.md | sed -n '/^```bash$/,/^```$/p' | sed '1d;$d')
```

Or copy-paste the function from `deleted_files.md` into your shell. Then:

```bash
del "old planning file, not referenced anywhere" .brand-list.txt
del "gitignored build artifacts, will rebuild on next build" .astro/ dist/ tina/__generated__/
del "OCR test fixtures, can regenerate via Tavily + pdf-tools" downloads/singer_31-15.pdf
```

`del` will:
1. Append a properly-formatted entry to `deleted_files.md` (with timestamp, paths, sizes, your reason).
2. Run `rm -rf` on the targets.
3. Print confirmation to stdout.

### Alternative: backfill manually

If you used a plain `rm` (or the function wasn't sourced), append an
entry to `deleted_files.md` manually using the same format. The exact
format doesn't matter as long as timestamp + path + size + reason are
present. Example:

```bash
cat >> deleted_files.md <<'EOF'

### `path/to/file` — deleted 2026-07-23 14:32:01 +06:00

**Reason:** backfilled entry (not run through `del` function).

| Path | Action |
|---|---|
| `path/to/file` | deleted (4.2 KB) |
EOF
```

## What counts as "deletion"

- `rm file` or `rm -rf dir/`
- IDE / file-manager delete
- `git rm file` (tracked-file deletion)
- Branch reset / `git reset --hard` that removes tracked files
- A build script or migration that wipes a directory
- `trash` / `gio trash` / IDE "move to trash"

## What does NOT need to be logged

- **Files inside `node_modules/`** — npm manages these, not the user.
- **Build cache directories auto-regenerated by tooling** (`.astro/`, `tina/__generated__/`, `dist/`) — *if* the agent is the one causing them to be wiped as a side effect (e.g. `npm run clean`), they don't need a per-file log. They DO need a log if you deliberately `rm -rf` them for cleanup.
- **Git reflog churn** — files that existed in earlier commits but aren't in HEAD. Git already tracks these; this log is for the working tree.

## Why this rule exists

- **Onboarding** — new agents / new developers can read `deleted_files.md`
  and immediately understand what was removed and why, without grepping
  git history.
- **Audit** — when a feature mysteriously breaks, this log often shows the
  culprit (e.g. "we deleted `downloads/` because it was OCR test fixtures"
  → then someone added a build step that reads from `downloads/`).
- **Cross-session continuity** — sessions end, but the rule and the log
  persist. Future agents see what previous agents removed.

## Commit convention

After backfilling or running `del`, commit the change as:

```bash
git add deleted_files.md
git commit -m "chore(deleted): log <paths> — <short reason>"
```

For tracked-file deletions (`git rm file`), commit the deletion
separately:

```bash
git rm file
git commit -m "chore: remove <file> — <reason>"
# then backfill deleted_files.md in a follow-up commit
```

The two-commit pattern keeps the *what* (git diff) and the *why*
(deleted_files.md) independently auditable.
